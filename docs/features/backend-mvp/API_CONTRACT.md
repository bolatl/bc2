# API contract

## Transport and ownership

Base path: `/api/v1`. Requests/responses use JSON and camelCase. Protected operations require the signed `lovelab_session` cookie binding couple ID and role. Browser clients must send credentials. The cookie is HttpOnly, SameSite=Lax, Path=/, valid for 30 days, and Secure when configured. Host frontend and API on the same site; cross-site deployments need a separate cookie/CSRF design. CORS allows configured frontend origins; it never grants ownership. API responses must not be cached. Public invite routes disclose neither onboarding profile nor raw session text. A missing/private resource returns 404 rather than revealing its owner.

Request JSON is a single object up to 32 KiB with unknown properties rejected. All required fields must be present with the declared type. IDs and invite tokens are opaque server-issued strings. Times are RFC 3339 UTC. Empty arrays/maps use `[]`/`{}`; nullable values use explicit `null`. The default response has no undeclared fields. There are no query filters, pagination, or client-supplied role/couple IDs.

Creation/join set a cookie; deletion expires it. `POST /fight-sessions` and `/skip-topic` accept `{}` or no body. All other POST requests require their listed JSON object. A cannot use its own cookie to join B; replay after B is occupied conflicts unless the browser already has that B identity. `POST /subscriptions/*` is restricted to role A; B shares the paid entitlement.

## State and business behavior

The prototype deployment uses `FUNNEL=full`, `FREE_TURNS=5`, and `ENABLE_REHEARSAL=true`: intensity, story, three brief contextual questions, then payment before rehearsal. Legacy unconfigured server defaults are noted below. `CreateCoupleRequest` requires only `relationshipStatus`, `conflictStyle`, and `repairNeed`; older profile fields remain accepted but optional.

| Session status | currentTurn | Raw history |
|---|---|---|
| in_progress | next_turn | Owner only |
| awaiting_payment | paywall_required | Owner only, preserved for continuation |
| completed | completed | Empty |
| stopped_safety | safety_stop | Empty |
| skipped | null | Empty |

- The first free session uses the configured teaser limit (default four accepted answers). Reaching it returns a paywall branch and preserves history for later continuation. New unpaid sessions are not a way to obtain unlimited teasers.
- The stages depend on `FUNNEL`. Short (default, five questions): `thermometer_start → facts → feelings → needs → [rehearsal] → ready`. Full (seven): `thermometer_start → facts → feelings → needs → partner_view → [rehearsal] → thermometer_end → ready`. Default rehearsal is off. In the short funnel `thermometerEnd` stays null. These are bounded by the server, not generated by an LLM. Stage progress is independent of total turn budget.
- Use a free-text integer string 1–10 for the thermometer scale; a supplied numeric card can also be selected. Other free text must be nonempty within the documented length. Card choice is resolved from the stored current question, never trusted as arbitrary client content.
- A successful turn either returns the next question, pauses for payment, privately stops for safety, or completes with a result path. Stale or duplicate indexes cannot advance state.
- Backtracking reopens an already answered index and erases its answer plus later branch data. Safety-stopped, skipped, and completed sessions cannot be resumed. Skip always erases raw text.
- Safety checks precede every LLM operation. After a stop, no crisis message, diagnosis, stopped status, or raw answer is propagated to the other partner.
- Follow-up generation receives this owner's prior questions, answer sources, and answers, with onboarding context and optional questionnaire trait levels. It anchors follow-ups to the described situation without repeating answered questions or attributing the partner's actions to the owner.
- Generated prompts use at most 12 words; cards at most eight words and 60 characters. Results may include `rehearsal: {optionA, optionB}` from the current rehearsal, including the unpaid preview; this is not a prediction of the partner’s reaction. The final selected or written respectful rehearsal sentence becomes the result’s opening line; a custom sentence follows the existing 300-character submit limit.
- The result is available at the teaser paywall as a preview, or after completion. Before a preview exists it is a conflict; a saved preview may remain readable while the paid session continues. Unpaid previews use an empty `openingLine` and `locked: ["openingLine", "inviteUrl"]`. Completed full results have `locked: []`; a paid but unfinished preview still has both locks.
- An invitation becomes shareable only after A has active payment and is ready. `inviteUrl` stays empty beforehand and for B. Joining requires the enabled opaque token. `partnerBInviteSentAt` means shareability in the current round, not proof of delivery; it resets when A starts a new round.
- Only one outstanding round is coordinated at a time. A may start another round after both completed, or after A stopped/skipped with no active B. A stopped/skipped B may retry a fresh private session in the same round. A new unpaid attempt after consuming the free teaser requires payment. The shared journal record is created exactly once only when both are ready.
- A rating updates the caller’s side. Explicit null means not discussed; a missing property is invalid. Two numeric ratings create an arithmetic mean; incomplete/not-discussed records remain gray. Mean <5 is red, 5–<8 yellow, and ≥8 green. Divergence compares raw ratings at the configured difference (default ≥4).
- Journal rows and rating trend are oldest first and omits missing averages. The recurring-topic hint selects the most frequent topic appearing at least three times over the stored journal (lexicographic tie-break), not a date-filtered window.
- Checkpoints (`ENABLE_CHECKPOINTS=true`, full tier only): in the short funnel after `feelings`; in the full funnel after `needs`, and after `partner_view` when a content stage (rehearsal) still follows, the answer to the turn returns `type: "checkpoint"` with an interim `summary` (`feltText`, `needText`, `openingLine`) instead of the next question. The same card is returned by `GET /fight-sessions/{id}` until resolved, and `/turns` answers conflict meanwhile. `POST .../checkpoint` with `{"decision":"continue"}` resumes the normal stage order; `{"decision":"stop"}` skips the remaining content stages and goes to the closing stage (`thermometer_end` in the full funnel, `ready` in the short one); `ready` completes as usual. A rewind (`/back`) clears a pending checkpoint. Disabled by default; clients unaware of the `checkpoint` branch never see it.
- Results may include a `reflection`: three to five qualitative themes with no percentages or diagnostic labels. Preview summary, labels, and explanations are visible, while practice is JSON null until full access. The report is generated at the teaser paywall and final readiness step, not on reads or checkpoints, and only a completed derived report is persisted. Older results can omit it.
- Result and reflection generation run concurrently and commit atomically. The reflection's own time budget or repeated invalid content can produce a basic answer-based reflection; its summary explicitly states that a detailed reflection could not be prepared. This is a successful response with the same access gates. Parent cancellation and other provider failures still return `503` without committing the answer. Generated prose is checked for respectful, non-graphic language even when the input is explicit.
- `GET /journal/{fightRecordId}` returns the shared record plus `myResult`, the caller's own private result for that round (or `null`). The partner's result is never included. Requires an active plan like the rest of the journal.
- Terminal cleanup removes raw answers, questions, and cards. Only private derived results and shared journal aggregates remain until the couple is deleted. Personality answers are separate and may be retained.
- Checkout confirmation is tied to the current couple and server-selected plan/amount. Stripe test mode requires a verified paid checkout; keyless mock mode verifies an issued checkout ID for the same couple and plan and then simulates success. Repeated valid confirmation is idempotent. A frontend redirect cannot activate access. Repeating checkout creation for the same pending plan returns the same ID/URL with 201; choosing a different plan while one is pending returns 409. A settled active couple cannot create another checkout. Mock creation returns a frontend `/checkout/demo?session_id=cs_mock_…&demo=true` URL; the browser presents the test-card form and submits only the checkout ID after local field validation. The API never receives cardholder name, card number, expiry, or CVC.

## Errors

| HTTP | Meaning |
|---|---|
| 400 | Invalid or malformed JSON request. |
| 401 | Anonymous session missing, invalid, or deleted. |
| 402 | Active payment is required. |
| 403 | Actor or request origin is not permitted. |
| 500 | Unexpected internal error. |
| 404 | Resource missing, private to another actor, or invitation unavailable. |
| 409 | State conflict, stale turn, occupied role, or incomplete payment. |
| 413 | Request exceeds body size limit. |
| 415 | Expected application/json. |
| 502 | Payment checkout provider unavailable. |
| 503 | Next session step or result could not be generated. |

Every error body is `{"code":"machine_code","message":"Display text"}`. Refer to each operation in OpenAPI for its applicable statuses. Business branches `safety_stop` and `paywall_required` are successful turn responses (200); an independently gated resource uses 402. Generation uses `503 generation_unavailable`; checkout creation uses `502 payment_unavailable`; failed payment verification uses `409 payment_unconfirmed`. Missing/private resources use `not_found`, authentication uses `unauthorized`, validation uses `validation_error`, other state conflicts use `conflict`, a stopped result uses `409 safety_blocked`, and paid-resource gates use `payment_required`. Global origin rejection is `403 forbidden_origin`; excessive payload is `413 payload_too_large`; wrong content type is `415 unsupported_media_type`; unexpected failures use `500 internal_error`. An unsupported method returns `405 method_not_allowed`. Provider failures never expose credentials or response bodies.

## Validate this contract

From the repository root, create an isolated validation environment and run:

```sh
python3 -m venv /tmp/lovelab-contract-venv
/tmp/lovelab-contract-venv/bin/pip install PyYAML jsonschema openapi-spec-validator
/tmp/lovelab-contract-venv/bin/python docs/features/backend-mvp/validate_contract.py
```
