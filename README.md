# Love Lab

Приложение для приватного разбора ссоры каждым из двух партнёров: API на Go 1.26 и chi, веб-интерфейс на React и TypeScript. Реализована 21 операция API: тест личности Mini-IPIP, подготовка к разговору с продолжением после оплаты, промежуточные итоги, приглашение партнёра, личные результаты, оценки и общий журнал с просмотром прошлых разговоров.

Исходные продуктовые документы `LoveLab_*.md`, корневой `SKILL.md` и `Business_Cup_2.0_Brief.pdf` остаются локальными материалами и исключены из Git через `.gitignore`. Документация реализованного API находится в [`docs/features/backend-mvp/`](docs/features/backend-mvp/).

После установки системных инструментов выполните:

```sh
make setup
```

Команда загружает Go-модули, выполняет `npm ci` в `frontend/`, создаёт локальное окружение `.venv`, устанавливает Python-пакеты и Chromium. Серверы запускаются отдельно по инструкции ниже. Установить только часть зависимостей можно командами `make setup-go`, `make setup-frontend`, `make setup-python` или `make setup-browser` (последняя также устанавливает npm-пакеты).

На свежем Linux/WSL для браузерных тестов дополнительно могут понадобиться системные библиотеки. После `make setup` установите их через [CLI Playwright](https://playwright.dev/docs/browsers#install-system-dependencies); команда может запросить права администратора:

```sh
cd frontend
npx --no-install playwright install-deps chromium
```

`requirements.txt` остаётся корректным входом для `pip`: системные Go/Node/Make устанавливаются отдельно, а их полный список приведён выше и в комментарии файла. Версии JavaScript- и Go-зависимостей не нужно вручную дублировать в Python-файле.

## Запуск интерфейса

Интерфейс находится в [`frontend/`](frontend/README.md): React, TypeScript и Vite. Бежевый интерфейс с сакурой включает анимацию движения по ветке между вопросами, личный кабинет, отдельный вид статуса партнёра и размытые превью закрытых разделов. Поддерживаются короткая и полная воронки, промежуточные проверки и личные итоги из журнала. Нужен Node.js 22.13+ в ветке 22 или 24+ (рекомендуется 24). Для проверки без внешних API запустите два терминала из корня проекта.

Первый — бэкенд с имитацией AI и оплаты:

```sh
LLM_API_KEY= LLM_PROVIDER= LLM_MODEL= LLM_BASE_URL= STRIPE_SECRET_KEY= make run
```

Второй — интерфейс:

```sh
cd frontend
npm ci
VITE_LLM_MODE=mock VITE_PAYMENT_MODE=mock npm run dev
```

Откройте **http://localhost:5173**. Можно пройти анкету, необязательный профиль, подготовку к разговору, демонстрационную оплату, пригласить партнёра, выставить оценки и открыть прошлый разговор из журнала. Приглашение B открывайте в отдельном профиле браузера или приватном окне. Без `DATA_FILE` перезапуск удаляет данные; с настроенным сохранением переживают перезапуск только профили, подписки, результаты теста и завершённых подготовок, журнал и оценки. Незавершённая подготовка не сохраняется на диск.

Для реальной генерации вместо первой команды используйте `make run-env` с уже настроенным корневым `.env`. Во втором терминале задайте `VITE_LLM_MODE=anthropic` или `openai` в соответствии с полем `llm_mode` в логе; `VITE_PAYMENT_MODE=mock` подходит только если `payment_mode=mock`. Эти публичные параметры меняют подписи интерфейса, а не провайдера/доступ. API-ключи хранятся только в корневом серверном `.env`. Без явной настройки интерфейс считает режим неизвестным.

Подробности запуска, проверки и ограничения: [`frontend/README.md`](frontend/README.md).

## Локальный запуск

```sh
go run ./cmd/server
```

API доступен по адресу `http://localhost:8080/api/v1`. При `GOTOOLCHAIN=auto` — это значение по умолчанию — современная установленная версия Go автоматически загрузит инструментарий Go 1.26. Для запуска не нужны база данных, API-ключи или учётная запись. Сервер предоставляет только API; фронтенд запускается отдельно.

В другом терминале можно пройти полный демонстрационный сценарий с тестовыми данными и независимыми cookie для двух партнёров:

```sh
python3 scripts/demo.py --delete-after
```

Ожидаемый результат: `PASS`, зелёная запись в общем журнале со средней оценкой `8.5` и подтверждение удаления исходных текстов разбора. Без `--delete-after` данные тестовой пары останутся на сервере и при включённом `DATA_FILE` попадут в файл истории.

## Настройка

Пример переменных окружения: [.env.example](.env.example). Перед запуском экспортируйте нужные значения в окружение: сервер не загружает `.env` автоматически.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `ADDR` | `:8080` | Адрес и порт HTTP-сервера |
| `FRONTEND_URL` | `http://localhost:5173` | Origin фронтенда для приглашений и перенаправлений после оплаты |
| `ALLOWED_ORIGINS` | Origin фронтенда | Разрешённые origin через запятую; проверяется точное совпадение |
| `SESSION_SECRET` | Криптографически случайное значение при каждом запуске | Секрет длиной не менее 32 символов для подписи cookie; при `DATA_FILE` обязателен постоянный явно заданный секрет |
| `COOKIE_SECURE` | `false` | Установите `true` при работе через HTTPS |
| `FREE_TURNS` | `4` | Число ответов до экрана оплаты: `3` или `4` |
| `MAX_TURNS` | `12` | Максимум ходов: `5..12` (`short`) или `7..12` (`full`); с репетицией минимум на 1 больше |
| `DIVERGENCE_THRESHOLD` | `4` | Минимальная разница оценок партнёров для сигнала о расхождении |
| `FUNNEL` | `short` | Длина воронки: `short` (5 вопросов: термометр, факты, чувства, потребности, готовность) или `full` (7, ещё «взгляд партнёра» и финальный термометр) |
| `ENABLE_REHEARSAL` | `false` | Включает дополнительный этап репетиции разговора |
| `DISABLE_PAYWALL` | `false` | `true` отключает пейвол: сессия идёт целиком без оплаты, приглашение партнёра и журнал доступны сразу. Только для локальной проверки |
| `DATA_FILE` | Пусто | Путь к JSON-файлу, куда сохраняются пары, журнал и личные итоги (права 0600). Требует постоянный `SESSION_SECRET`. Сырые ответы не пишутся |
| `ENABLE_CHECKPOINTS` | `false` | Промежуточный итог после `feelings` в short или `needs` в full; после `partner_view` — только при репетиции. Пользователь продолжает или переходит к финальным вопросам |
| `STRIPE_SECRET_KEY` | Пусто | Без ключа используется мок оплаты; `sk_test_…` включает тестовый режим Stripe |
| `LLM_API_KEY` | Пусто | Ключ OpenAI или Anthropic. Без ключа используется детерминированный мок (тексты не покидают сервер); с ключом вопросы, тема и итог генерируются моделью. Термометры и этап `ready` остаются детерминированными |
| `LLM_PROVIDER` | Авто | `openai` или `anthropic`; если пусто, определяется по префиксу ключа (`sk-ant-` → Anthropic) |
| `LLM_MODEL` | `claude-opus-5-5` / `gpt-4o-mini` | Модель; по умолчанию зависит от провайдера |
| `LLM_BASE_URL` | Официальный API | Базовый URL (прокси или совместимый сервер) |

По умолчанию `FUNNEL=short`: начальный термометр, факты, чувства, потребности и подтверждение готовности — пять ответов. `FUNNEL=full` добавляет возможную точку зрения партнёра и финальный термометр; репетиция добавляет ещё один этап в любом режиме. Значение термометра передаётся с `answerSource: "free_text"` и `answerText` от `"1"` до `"10"`; также можно выбрать одну из предложенных числовых карточек.

Свой ответ ограничен 300 кодовыми точками Unicode. Интерфейс показывает счётчик и блокирует превышение; Enter отправляет ответ, Shift+Enter добавляет строку. При `ENABLE_CHECKPOINTS=true` промежуточный итог предлагает **Continue** или **Wrap up**. Второй вариант пропускает оставшиеся содержательные вопросы, но готовность всё равно нужно подтвердить. Боковые этапы следуют состоянию API без фиксированных семи шагов. В коротком режиме итог показывает начальную интенсивность; значения «после» в нём нет.

## Подключение фронтенда

Для `fetch` укажите `credentials: "include"`. Размещайте фронтенд и API в пределах одного сайта с точки зрения браузерной политики SameSite. Cookie используют `HttpOnly`, `SameSite=Lax` и, при соответствующей настройке, `Secure`. Запросы из браузера с неразрешённых origin отклоняются. Локальные настройки поддерживают связку `localhost:5173` → `localhost:8080`.

У всех API-маршрутов ниже префикс `/api/v1`.

1. Создайте пару от имени A через `POST /couples`. При запуске разбора сохраните `sessionId`; для восстановления состояния используйте `GET /fight-sessions/{sessionId}`.
2. Отображайте `currentTurn` или ответ `/turns` в зависимости от поля `type`. На этапах термометра `progressStageIndex` равен `null`. При выборе карточки можно не передавать `answerText`: сервер возьмёт сохранённый текст карточки.
   При `type: "checkpoint"` покажите личный `summary` и отправьте `POST /fight-sessions/{id}/checkpoint` с `decision: "continue"` или `"stop"`. Ответ снова имеет тип `TurnResponse`; пока checkpoint не закрыт, `/turns` возвращает `409`.
3. При `paywall_required` создайте платёжную сессию и перенаправьте пользователя на `checkoutUrl`. После возврата передайте полученный `session_id` в поле `checkoutSessionId` запроса `POST /subscriptions/confirm`. Загрузите разбор с прежним ID: он продолжится с того же вопроса.
4. После подтверждения готовности партнёром A ответ `GET /couples/me` содержит `inviteUrl`. На фронтенде нужны страницы `/invites/{token}`, `/checkout/success` и `/checkout/cancel`.
5. Откройте приглашение B в **отдельном профиле браузера или приватном окне с отдельным хранилищем cookie**. Обычная соседняя вкладка использует cookie партнёра A. Загрузите превью приглашения, отправьте три ответа анкеты B и начните его разбор.
6. Периодически запрашивайте `/couples/me` или личный результат разбора, чтобы обновлять статус готовности партнёра. SMS, email и push-уведомления не отправляются.
7. Когда оба партнёра закончат разбор, загрузите `/journal`, отправьте оценки по ID записи и запросите `/journal/stats`. Страница интерфейса `/journal/:recordId` получает `GET /journal/{fightRecordId}`: общие поля записи и только личный `myResult` текущего партнёра. `myResult` может быть `null`; общая запись при этом остаётся доступной. **Check in** открывает оценку того же разговора. В демонстрации ждать вечера не нужно.

Ссылка-приглашение остаётся пустой, пока A не оплатит и не завершит текущий разбор. Приглашение можно принять один раз; повторное присоединение требует существующей cookie партнёра B. При начале нового разбора ссылка снова становится доступной только после готовности A. Каждый партнёр имеет доступ только к собственным сессиям и результатам теста личности.

Повторное создание платёжной сессии для того же ожидающего оплаты тарифа возвращает прежнюю сессию. Пока она ожидает оплаты, выбрать другой тариф нельзя: сначала нужно подтвердить текущую оплату. При активной подписке API не создаёт новую платёжную сессию.

## Режимы оплаты

Без ключа Stripe платёжная сессия сразу перенаправляет на страницу успешной оплаты фронтенда с `demo=true` и ID вида `cs_mock_…`. Подтверждение имитирует оплату локально. На фронтенде этот режим должен быть явно обозначен как демонстрационный.

Для тестового режима Stripe экспортируйте тестовый секретный ключ и перезапустите сервер. Используйте карту `4242 4242 4242 4242`, любую будущую дату окончания действия и любой трёхзначный CVC. Перед открытием доступа сервер получает платёжную сессию из Stripe и проверяет тестовый режим, завершение и успешную оплату, принадлежность паре, тариф, валюту и сумму. Тарифы: $14.99 в месяц, $99 в год или $149 за программу. Месячный и годовой тарифы оформляются как подписки, программа — как разовая покупка. Подробнее: [тестирование Stripe](https://docs.stripe.com/testing) и [платёжные сессии Checkout](https://docs.stripe.com/api/checkout/sessions).

В MVP нет вебхуков, синхронизации продлений и эндпоинта отмены подписки. Удаление данных приложения также удаляет локальные записи мока оплаты, но не отменяет подписку Stripe и не удаляет данные на стороне Stripe. Сетевые операции с настоящим тестовым аккаунтом Stripe не входили в локальную автоматическую проверку.

Есть известное ограничение восстановления mock-оплаты: если при заданном `DATA_FILE` перезапустить сервер между созданием checkout и его подтверждением, сохранённая подписка ссылается на checkout, которого больше нет в памяти мока. Повторное открытие возвращает тот же ID, а подтверждение — `409 payment_unconfirmed`; повтор запроса из интерфейса это не исправляет. Уже активная подписка восстанавливается нормально.

## Приватность и безопасность

Проверка безопасности выполняется перед каждой операцией LLM и до принятия текста пользователя. При обнаружении кризисных формулировок личная сессия останавливается, её исходные тексты удаляются, а пользователь получает контакты помощи для США. Причина остановки, сообщение и изменение статуса не передаются другому партнёру. Фильтр использует набор английских и русских фраз и не гарантирует распознавание всех кризисных ситуаций. Целевая аудитория MVP — пары в США.

После завершения, пропуска или остановки по безопасности исходные ответы и сгенерированные вопросы не сохраняются. Личные результаты завершённого разбора содержат производные формулировки; общий журнал — только тему, даты, оценки и рассчитанные показатели. У незавершённых сессий, в том числе ожидающих оплаты, собственная история сохраняется для перезагрузки страницы и продолжения разбора. `DELETE /couples/me` удаляет локальные данные пары; после этого обе cookie перестают давать доступ. В HTTP-логах используются шаблоны маршрутов без токенов приглашений, тел запросов и cookie.

Без `DATA_FILE` все данные в памяти исчезают при перезапуске. Если путь задан, завершённые результаты, журнал, профили и подписки сохраняются в JSON с правами `0600`; сырые ответы, вопросы, карточки и незавершённые сессии не записываются. Сохранение выполняется в фоне и при штатной остановке. Для прежних cookie нужен тот же `SESSION_SECRET`. API не раскрывает режим сохранения, поэтому интерфейс описывает его условно.

После перезапуска URL незавершённой подготовки возвращает `404`, а `currentSessionId` становится `null`. При этом факт использования бесплатного разбора A сохраняется: повторный запуск потребует полного доступа (`402`). Если исчезла подготовка B, завершённый результат A сохраняется и B может начать свою часть заново; до этого сохранённый статус B может оставаться `in_progress`. Регистрации и восстановления доступа при утрате cookie нет. Операции, затрагивающие несколько хранилищ сущностей, выполняются последовательно на уровне сервиса. MVP рассчитан на демонстрацию в одном процессе.

Python-зависимости для проверки контракта собраны в [`requirements.txt`](requirements.txt): `PyYAML`, `jsonschema` с проверкой форматов, `referencing` и `openapi-spec-validator` для полной проверки OpenAPI. Установите их в локальное виртуальное окружение; каталог `.venv/` уже исключён из Git:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python docs/features/backend-mvp/validate_contract.py

go test -race ./...
go vet ./...
go build -o bin/lovelab ./cmd/server
```

Для работы приложения Python-пакеты не нужны: зависимости бэкенда описаны в `go.mod` и `go.sum`, фронтенда — в `frontend/package.json` и `frontend/package-lock.json`. Скрипт `scripts/demo.py` использует только стандартную библиотеку Python. Тесты проверяют основной HTTP-сценарий, аутентификацию и права доступа, валидацию запросов, конкурентную отправку одного хода, порядок проверок безопасности, возврат к предыдущим шагам, продолжение после оплаты, подмену платёжных данных, разделение записей разных разборов, подсчёт баллов, оценки и удаление данных.

Для проверки ответов работающего сервера в режиме мока оплаты выполните `.venv/bin/python docs/features/backend-mvp/validate_contract.py --live-url http://localhost:8080`. Проверка создаёт и удаляет тестовые пары. После объединения изменений прошли `go vet ./...`, `go test -race ./...`, проверки TypeScript и ESLint. Спецификация описывает 21 операцию API.

Браузерные наборы запускаются из `frontend/`:

```sh
npm run test:e2e
npm run test:e2e:v2
```

Первый набор содержит девять сценариев полной воронки, личных страниц и дизайна с mock-оплатой (Go `18080`, Vite `5174`; checkpoints выключены). Второй проверяет короткую воронку, промежуточные итоги и историю (Go `18082`, Vite `5176`; checkpoints включены, пейвол отключён). Оба набора используют синтетические данные, очищают внешние ключи, отключают запись `DATA_FILE` и разделяют браузеры A/B. Свободные тестовые порты обязательны. Оба набора пройдены: 9 основных сценариев (включая 3 проверки нового дизайна) и 5 сценариев v2. Также прошли production-сборка и статическая проверка контракта (21 операция, 54 схемы, 43 примера); дополнительный валидатор полного документа OpenAPI в этом прогоне не установлен.

Для сборки контейнера выполните `docker build -t lovelab-backend .`. Перед запуском настройте origin фронтенда и параметры cookie для HTTPS под целевое окружение. Сборка контейнера и развёртывание не входили в локальные проверки Go.
