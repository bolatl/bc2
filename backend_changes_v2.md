# Backend changes v2: история на диске, просмотр прошлых ссор, промежуточные проверки

Продолжение `backend_changes_v1.md`: хранение истории, просмотр прошлых разборов, промежуточные проверки и короткая воронка. Ниже описаны изменения API и поддержка этих возможностей в веб-интерфейсе.

## Новые переменные окружения

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATA_FILE` | пусто | Путь к JSON-файлу с историей, например `data/lovelab.json`. Пусто: всё только в памяти |
| `SESSION_SECRET` | случайный при старте | Обязателен, если задан `DATA_FILE`, не короче 32 символов. Без него куки сбрасываются при перезапуске |
| `ENABLE_CHECKPOINTS` | `false` | Включает промежуточные проверки посередине сессии |
| `FUNNEL` | `short` | `short`: 5 вопросов, `full`: 7 (см. раздел 4) |

Для сохранения истории задайте `DATA_FILE`, например `data/lovelab.json`, и постоянный `SESSION_SECRET` в серверном окружении. Значения локального `.env` не являются частью контракта. Папка `data/` исключена из Git. API не сообщает интерфейсу, включено ли сохранение, поэтому текст в настройках описывает оба режима.

## 1. Локальное хранение истории

Если задан `DATA_FILE`, бэкенд сохраняет данные в JSON и читает их при старте. Журнал, личные итоги, пары и подписки переживают перезапуск.

- **Что пишется:** пары (профили, токен приглашения), подписки, результаты теста личности без сырых ответов, завершённые сессии с итогом, журнал с оценками.
- **Что не пишется никогда:** сырые ответы, сгенерированные вопросы и карточки, незавершённые сессии (проверено тестом). Это то же правило приватности, что и в памяти: после завершения сессия не хранит текст ответов.
- **Как пишется:** в фоне через 250 мс после изменения, атомарно (временный файл и переименование), права `0600`; финальное сохранение при остановке сервера (`Ctrl+C`).
- **Ошибки:** повреждённый файл останавливает запуск с понятной ошибкой и не затирается. Отсутствующий файл нормален.
- **Удаление:** `DELETE /couples/me` удаляет данные пары из памяти; фоновое сохранение переносит удаление в файл.
- **Ограничение:** незавершённая сессия после перезапуска теряется. Её старый URL возвращает `404`, а `currentSessionId` в `/couples/me` становится `null`. Возвращаться следует через главную страницу; доступ к новому разбору по-прежнему проверяет сервер. Файл содержит профили, токены и личные тексты итогов, поэтому его нельзя коммитить.

Два ограничения восстановления важно учитывать при проверке:

- У использовавшего бесплатный разбор партнёра A сохраняется `FreeSessionUsed`, даже если сам разбор не завершён. После перезапуска начать его заново бесплатно нельзя: сервер отвечает `402` и предлагает открыть полный доступ. Если потеряна подготовка B, завершённая подготовка A остаётся доступной, и B может начать свою заново; сохранённый статус B до этого может оставаться `in_progress`.
- **Известная ошибка мока оплаты:** незавершённый checkout сохраняется в подписке, но внутреннее состояние провайдера mock не восстанавливается. После перезапуска повторное открытие возвращает тот же checkout, а подтверждение отвечает `409 payment_unconfirmed`. Фронтенд не может исправить это повтором запроса. Уже активные подписки восстанавливаются; исправление незавершённого mock-checkout относится к бэкенду.

Реализация: `internal/service/persist.go`; репозитории получили хук `OnChange` (`internal/repository/memory.go`).

## 2. Просмотр прошлых ссор

`GET /api/v1/journal/{fightRecordId}` возвращает общую запись журнала и поле `myResult`: личный итог вызывающего партнёра за этот раунд (`feltText`, `needText`, `openingLine`, `sharedRules`, термометры). Поля записи находятся в корне ответа, а `myResult` может быть `null`. Итога партнёра в ответе нет, чужой или неизвестный `id` даёт `404`; без полного доступа — `402`. Список записей остаётся в `GET /journal`. Запись появляется, когда оба партнёра завершили подготовку.

В интерфейсе запись открывается на `/journal/:recordId`: общие тема, даты и оценки отделены от личного итога текущего партнёра. При `myResult: null` общая запись остаётся доступной, а интерфейс сообщает, что личного итога нет. Кнопка **Check in** ведёт к оценке этого же разговора. Личные данные разделяются по паре и роли браузера и не сохраняются в localStorage/sessionStorage.

Со `DATA_FILE` эти итоги доступны и после перезапуска бэкенда.

## 3. Промежуточные проверки

При `ENABLE_CHECKPOINTS=true` можно завершить содержательную часть раньше. Следующий пример относится к `FUNNEL=full`; для короткого режима различия указаны ниже:

1. После ответа на этап `needs` вместо следующего вопроса приходит
   ```json
   {"type":"checkpoint","afterStage":"needs","summary":{"feltText":"…","needText":"…","openingLine":"…"},"question":"Does this feel right so far? You can stop here or keep going.","decisions":["stop","continue"]}
   ```
   Промежуточный итог пишет модель по ответам до этого момента (тот же вызов, что и для финального итога, с той же защитой и проверкой запрещённых слов).
2. `POST /api/v1/fight-sessions/{id}/checkpoint`:
   - `{"decision":"continue"}` возвращает обычный порядок (дальше `partner_view`);
   - `{"decision":"stop"}` пропускает оставшиеся содержательные этапы и ведёт к `thermometer_end`, затем `ready`. Поэтому готовность обоих партнёров, журнал и итог работают как обычно.
3. Пока проверка не закрыта, `GET /fight-sessions/{id}` показывает её же, а ходы `/turns` отвечают `409`. `/back` сбрасывает незакрытую проверку.
4. **Второй checkpoint** (после `partner_view`) появляется, только если после него остаётся содержательный этап, то есть при `ENABLE_REHEARSAL=true`. Без репетиции остаются лишь финальные шаги, и «стоп» и «продолжить» ничем бы не отличались.
5. **На бесплатной части (тизер) проверок нет**, там свой лимит `FREE_TURNS`.

Фронтенд обрабатывает `checkpoint` как отдельный экран с личным промежуточным итогом. **Continue** отправляет `decision: "continue"`, **Wrap up** — `decision: "stop"`. Wrap up не отмечает пользователя готовым автоматически: интерфейс показывает оставшиеся финальные вопросы и ждёт явного подтверждения на этапе `ready`. Доступны **Back** и **Skip this topic**. После перезагрузки незакрытый checkpoint загружается из API; при неопределённом результате запроса интерфейс сверяет состояние перед следующей отправкой. Флаг остаётся выключенным по умолчанию и включается на сервере.

## 4. Короткая воронка и лимиты на длину

Воронка и тексты стали короче.

**Воронка (`FUNNEL`).** По умолчанию `short`, пять вопросов: `thermometer_start`, `facts`, `feelings`, `needs`, `ready`. Убраны `partner_view` и финальный `thermometer_end` (в итоге `thermometerEnd` равен `null`). `FUNNEL=full` возвращает прежние семь вопросов. `progressStageIndex` в коротком режиме считает реально существующие этапы (`facts`=1, `feelings`=2, `needs`=3, `ready`=4), в полном остаётся прежняя нумерация. `MAX_TURNS` теперь допускает минимум 5 (7 для `full`).

**Проверки посередине** в коротком режиме приходят после `feelings` (остановка ведёт сразу к `ready`), в полном как раньше после `needs` и `partner_view`.

**Отображение.** Интерфейс следует `currentTurn.type` и серверному этапу; боковой список не навязывает семь шагов или отсутствующий этап взгляда партнёра. `turnsMax` — лимит ответов, а не обещание точного количества вопросов. Когда `thermometerEnd: null`, итог показывает только начальную интенсивность без выдуманного значения «после». `ENABLE_REHEARSAL=true` добавляет этап репетиции в обоих режимах; нижняя граница `MAX_TURNS` увеличивается на один.

**Лимиты на длину.**

| Что | Лимит |
|---|---|
| Свой ответ пользователя | 300 кодовых точек Unicode (раньше 4000); сервер отвечает `400`, фронт показывает счётчик `N / 300` и блокирует отправку превышения |
| Вопрос модели | не больше 18 слов, до двух коротких фраз |
| Карточка | не больше 8 слов (раньше 12) |
| Итог: `feltText`, `needText` | до 20 слов каждое |
| Итог: `openingLine` | до 25 слов |
| Итог: каждое из трёх правил | до 12 слов |

Лимиты записаны в системном промпте, и модель не обязана их соблюдать, поэтому сервер их проверяет. Если ответ слишком длинный (или в нём запрещённое слово), модели один раз повторно отправляется запрос с просьбой быть короче. Если и второй ответ нарушает лимит, вместо него используется готовый шаблонный вопрос или итог, а не ошибка 503. В лог пишется предупреждение (`generated question rejected`). Ошибки транспорта и ответы не по схеме по-прежнему возвращают `503`.

Длинный ввод пользователя не раздувает ответ: в промпте указано не цитировать и не повторять его текст, а сам ввод ограничен 300 кодовыми точками Unicode. На клиенте используется `[...text].length`, на сервере — подсчёт рун; составной emoji может занимать несколько кодовых точек. Одинаковое ограничение применяется к кнопке отправки и Enter; Shift+Enter вставляет перенос строки.
